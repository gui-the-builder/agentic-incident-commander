# Specification: Local-First Agentic Incident Commander

**Feature ID:** 001-local-incident-commander  
**Status:** Draft for implementation  
**Primary objective:** Demonstrate reliable agentic incident response against a fully local simulated production environment.

---

## 1. Problem statement

Production incident response requires gathering evidence across logs, metrics, service state, configuration, and recent changes. Human responders repeatedly perform the same investigation loop:

1. understand the alert;
2. inspect system evidence;
3. form hypotheses;
4. test hypotheses;
5. decide on remediation;
6. execute changes safely;
7. verify recovery;
8. document what happened.

This project builds an AI incident commander that performs that loop using explicit tools and a stateful workflow.

The system is not intended to replace human operators. It is designed to show how an agent can perform bounded operational reasoning while preserving safety, traceability, and human control.

---

## 2. Goals

### G1 — Local-first execution

The complete MVP MUST run on a developer laptop without requiring any cloud account.

Default runtime:

- Docker Compose
- Python 3.12+
- FastAPI
- PostgreSQL
- Prometheus
- Grafana
- Loki or structured log search through a local adapter
- OpenTelemetry
- Ollama
- LangGraph

A later milestone MAY add kind/k3d for Kubernetes-specific incidents.

### G2 — Stateful incident workflow

The agent MUST implement an explicit workflow with the following logical states:

```text
RECEIVED
  ↓
CONTEXT_GATHERING
  ↓
HYPOTHESIS_GENERATION
  ↓
INVESTIGATION
  ↓
DIAGNOSED
  ↓
REMEDIATION_PLANNED
  ↓
AWAITING_APPROVAL ── if action is risky
  ↓
EXECUTING
  ↓
VERIFYING
  ↓
RESOLVED | ESCALATED | FAILED
  ↓
POSTMORTEM_GENERATED
```

### G3 — Evidence-backed reasoning

Every diagnosis MUST reference evidence gathered through tools.

Each evidence item MUST record:

- source/tool;
- query or operation;
- timestamp;
- summarized observation;
- raw-result reference or persisted payload;
- confidence/relevance metadata where applicable.

A final diagnosis without supporting evidence MUST fail validation.

### G4 — Safe remediation

Actions MUST be classified by risk.

Example policy:

| Risk | Examples | Behavior |
|---|---|---|
| read-only | query logs, read metrics, inspect health | execute automatically |
| low | restart one demo worker, clear a test cache | configurable auto-execute |
| medium | restart service, change replica count | approval required by default |
| high | database mutation, destructive command | blocked in MVP unless explicitly allowlisted |

The agent MUST NOT execute arbitrary shell commands generated by the LLM.

### G5 — Reproducible incidents

The environment MUST contain deterministic scenario injectors so a reviewer can trigger known failures repeatedly.

At least three scenarios are required for portfolio MVP.

### G6 — Observable agent behavior

The system MUST expose:

- incident state;
- tool calls;
- tool latency;
- errors/retries;
- hypotheses;
- selected diagnosis;
- approvals;
- remediation actions;
- verification result;
- token/model metadata where available;
- total run duration.

---

## 3. Non-goals

The MVP does NOT need to:

- connect to a real cloud account;
- manage real production infrastructure;
- execute unrestricted operating-system commands;
- support arbitrary third-party services;
- provide a polished commercial UI;
- implement fully autonomous destructive remediation;
- solve every incident with an LLM.

Rule-based safeguards and deterministic validators are encouraged.

---

## 4. Primary user stories

### US1 — Start an incident

As an operator, I want to start an incident investigation from an alert so the agent can gather evidence and diagnose the issue.

**Acceptance criteria**

- API accepts alert title, service, severity, and optional description.
- Incident receives a unique ID.
- Workflow starts asynchronously or through a controlled worker.
- Current state can be queried.

### US2 — Observe investigation

As an operator, I want to see what tools the agent used and what evidence it collected.

**Acceptance criteria**

- Tool invocations are persisted.
- Evidence is tied to the incident.
- Tool errors are visible.
- The operator can inspect the incident timeline.

### US3 — Review hypotheses

As an operator, I want to see competing hypotheses and why one was selected.

**Acceptance criteria**

- Agent generates one or more hypotheses.
- Each hypothesis has supporting and contradicting evidence.
- Hypothesis confidence is explicit.
- Diagnosis selection is recorded.

### US4 — Approve remediation

As an operator, I want risky remediation to require my approval.

**Acceptance criteria**

- Risk classifier runs before execution.
- Medium/high actions transition to `AWAITING_APPROVAL`.
- Approval or rejection is persisted.
- Rejected plans are not executed.

### US5 — Verify recovery

As an operator, I want the agent to verify that remediation fixed the issue.

**Acceptance criteria**

- Verification queries the same or equivalent signals used to detect the problem.
- Resolution requires explicit success criteria.
- If verification fails, the incident returns to investigation or escalates.

### US6 — Generate postmortem

As an operator, I want a concise incident report after completion.

**Acceptance criteria**

Report includes:

- summary;
- impact;
- timeline;
- root cause;
- evidence;
- remediation;
- verification;
- follow-up actions;
- confidence/unknowns.

## 5. Functional requirements

### FR-001 Incident creation

The system MUST expose an API to create an incident.

### FR-002 Agent state persistence

Workflow state MUST survive process restarts.

For MVP, PostgreSQL persistence is preferred.

### FR-003 Structured tool interface

All tools MUST expose typed inputs and outputs.

Initial read tools:

- `get_service_health`
- `query_metrics`
- `query_logs`
- `get_recent_deployments`
- `get_service_config`
- `query_database_readonly`

Initial action tools:

- `restart_demo_service`
- `set_demo_feature_flag`
- `scale_demo_worker`

### FR-004 Tool timeout and retry

Each tool MUST define:

- timeout;
- retry count;
- retryable errors;
- idempotency expectation.

### FR-005 Hypothesis model

A hypothesis MUST contain:

```text
id
statement
supporting_evidence_ids[]
contradicting_evidence_ids[]
confidence
status
```

### FR-006 Diagnosis validator

Before remediation planning, the system MUST validate that:

- at least one hypothesis exists;
- selected diagnosis has supporting evidence;
- confidence is within an allowed range;
- required tool failures are acknowledged.

### FR-007 Remediation policy

Every remediation action MUST be checked by a deterministic policy engine before execution.

### FR-008 Approval

Approval MUST be an explicit API action.

### FR-009 Verification

Every executable remediation MUST define verification criteria before execution.

### FR-010 Scenario injection

The scenario controller MUST expose a command/API for injecting and resetting demo failures.

### FR-011 Postmortem

Completed incidents MUST generate Markdown postmortems.

### FR-012 Local model support

The default model integration MUST support Ollama through configuration.

Optional providers MAY be added behind the same model adapter.

---

## 6. Non-functional requirements

### NFR-001 Safety

No model-generated arbitrary shell execution.

### NFR-002 Auditability

All tool calls and state transitions MUST be timestamped and persisted.

### NFR-003 Determinism

Scenario injection MUST produce reproducible observable symptoms.

### NFR-004 Developer experience

A fresh clone SHOULD be runnable with no more than:

```bash
make bootstrap
make up
```

excluding the one-time installation of Docker and Ollama.

### NFR-005 Testability

Agent orchestration MUST be testable with a fake model and fake tools.

### NFR-006 Performance

For the local MVP, a typical incident SHOULD complete investigation within 2 minutes when the local model and tools respond normally.

### NFR-007 Portability

The code MUST not depend on a specific cloud provider.

---

## 7. Success metrics

Portfolio MVP target:

- ≥ 90% correct root-cause identification on deterministic happy-path scenarios;
- 100% enforcement of approval policy in automated tests;
- 0 arbitrary shell execution paths;
- ≥ 90% successful recovery on supported remediation scenarios;
- full trace for 100% of runs;
- all three required scenarios runnable from one command.

---

## 8. Required MVP scenarios

1. Checkout latency caused by database connection-pool exhaustion.
2. Elevated 5xx rate caused by a bad feature flag or configuration.
3. Worker backlog caused by a stalled worker process.

Detailed definitions live in `scenarios.md`.

---

## 9. Open design constraints

- Prefer explicit state over hidden conversational memory.
- Prefer typed tool results over natural-language scraping.
- Prefer deterministic safety rules over model judgment.
- Keep the first implementation small enough to finish.
- The agent MAY be a single LangGraph workflow; multi-agent decomposition is not required for MVP.
